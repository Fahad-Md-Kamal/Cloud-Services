# Lambda Function Guide

This document explains how the Lambda function in this project works, how it is deployed, and how it is triggered.

## 1. Purpose

The Lambda function is the processing engine of this project.

Its job is to:

1. Receive an S3 event when a new file is uploaded to the `file-uploads` bucket.
2. Detect whether the uploaded file is a supported CSV or image.
3. Download the file from S3.
4. Extract metadata from the file.
5. Store the extracted metadata in DynamoDB.

The implementation lives in [app/handler.py](/Users/fahadmdkamal/Desktop/serverless/app/handler.py).

## 2. High-Level Flow

The full flow is:

1. A file is uploaded into `file-uploads`.
2. S3 emits an `ObjectCreated` event.
3. S3 invokes the Lambda function `file-processor`.
4. Lambda reads the event payload.
5. Lambda downloads the file from S3.
6. Lambda extracts metadata depending on file type.
7. Lambda writes the result into DynamoDB table `file-processing-results`.
8. The FastAPI app can read the stored results through `/files` and `/files/{file_id}`.

## 6. Common Result Structure

Before storing anything, the code creates a shared metadata shape with:

- `file_id`
- `bucket`
- `object_key`
- `file_type`
- `content_type`
- `uploaded_at`
- `processed_at`
- `file_size`
- `status`
- `error_message`

This happens in:

- [app/handler.py](/Users/fahadmdkamal/Desktop/serverless/app/handler.py#L61)

Important detail:

- `file_id` is the S3 object key.

That means DynamoDB uses the object key as the primary identifier. If the same key is uploaded again, the existing item will be overwritten.

Another important detail:

- `uploaded_at` is not coming from S3 metadata.
- It is generated inside the Lambda at processing time.

So `uploaded_at` and `processed_at` are currently both generated by Lambda and can be very close or identical.

## 7. How CSV Processing Works

CSV processing starts in:

- [app/handler.py](/Users/fahadmdkamal/Desktop/serverless/app/handler.py#L83)

The sequence is:

1. Download the object from S3.
2. Read the bytes.
3. Decode bytes as UTF-8 text.
4. Parse rows with Python's `csv.reader`.
5. Use the first row as headers.
6. Count remaining rows as data rows.
7. Count headers to get the number of columns.
8. Store the metadata in DynamoDB.

The S3 object download happens through:

- [app/handler.py](/Users/fahadmdkamal/Desktop/serverless/app/handler.py#L77)

The CSV-specific extracted fields are:

- `row_count`
- `column_count`
- `headers`

Those are added in:

- [app/handler.py](/Users/fahadmdkamal/Desktop/serverless/app/handler.py#L100)

If CSV parsing fails, the function creates an error result instead of crashing the whole file-processing path:

- [app/handler.py](/Users/fahadmdkamal/Desktop/serverless/app/handler.py#L111)

## 8. How Image Processing Works

Image processing starts in:

- [app/handler.py](/Users/fahadmdkamal/Desktop/serverless/app/handler.py#L115)

The sequence is:

1. Download the object from S3.
2. Read raw bytes.
3. Inspect the binary file signature.
4. Parse image metadata directly from the file header.
5. Store the metadata in DynamoDB.

The extracted fields are:

- `image_format`
- `width`
- `height`

These are merged into the common result in:

- [app/handler.py](/Users/fahadmdkamal/Desktop/serverless/app/handler.py#L125)

### 8.1 PNG

PNG detection and parsing:

- [app/handler.py](/Users/fahadmdkamal/Desktop/serverless/app/handler.py#L147)

The code checks for the PNG signature and reads width and height from the IHDR chunk.

### 8.2 JPEG

JPEG detection and parsing:

- entry: [app/handler.py](/Users/fahadmdkamal/Desktop/serverless/app/handler.py#L151)
- parser: [app/handler.py](/Users/fahadmdkamal/Desktop/serverless/app/handler.py#L168)

JPEG does not keep width and height in a single fixed offset like PNG, so the code scans through JPEG markers until it finds a Start Of Frame marker, then reads dimensions from that segment.

### 8.3 GIF

GIF detection and parsing:

- [app/handler.py](/Users/fahadmdkamal/Desktop/serverless/app/handler.py#L154)

Width and height are read from the logical screen descriptor.

### 8.4 BMP

BMP detection and parsing:

- [app/handler.py](/Users/fahadmdkamal/Desktop/serverless/app/handler.py#L158)

Width and height are read directly from the BMP header.

### 8.5 WEBP

WEBP detection and parsing:

- entry: [app/handler.py](/Users/fahadmdkamal/Desktop/serverless/app/handler.py#L162)
- parser: [app/handler.py](/Users/fahadmdkamal/Desktop/serverless/app/handler.py#L219)

WEBP is handled through three internal chunk types:

- `VP8 `
- `VP8L`
- `VP8X`

Each one stores dimensions differently, so the parser has separate branches for each.

### 8.6 Why No Pillow

This project intentionally avoids an image-processing dependency such as Pillow.

Reason:

- the deployment script packages only the `app/` directory into the Lambda zip
- pure standard-library parsing keeps deployment simple in LocalStack
- no compiled native image library is needed

That packaging step is in:

- [scripts/deploy_lambda.sh](/Users/fahadmdkamal/Desktop/serverless/scripts/deploy_lambda.sh#L17)

## 9. Error Handling Strategy

There are two levels of error handling.

### 9.1 File-level errors

If a CSV or image file cannot be processed, the code generates an error item with:

- `status: "error"`
- `error_message`

This logic is centralized in:

- [app/handler.py](/Users/fahadmdkamal/Desktop/serverless/app/handler.py#L139)

This is useful because failed files are still visible in DynamoDB.

### 9.2 Invocation-level errors

If something fails outside the per-file processing flow, the outer handler catches it and returns a 500 response:

- [app/handler.py](/Users/fahadmdkamal/Desktop/serverless/app/handler.py#L48)

One implication:

- if an event contains multiple S3 records and one later record fails at the top level, some earlier records may already have been processed and stored.

## 12. How It Is Triggered

The trigger is not inside the Python code.

It is configured during deployment through S3 bucket notification setup:

- [scripts/deploy_lambda.sh](/Users/fahadmdkamal/Desktop/serverless/scripts/deploy_lambda.sh#L99)

The bucket notification says:

- bucket: `file-uploads`
- event: `s3:ObjectCreated:*`
- destination: Lambda `file-processor`

That means any new object creation in `file-uploads` should invoke the Lambda.

The deploy script also grants S3 permission to invoke the Lambda:

- [scripts/deploy_lambda.sh](/Users/fahadmdkamal/Desktop/serverless/scripts/deploy_lambda.sh#L91)

Without that permission, the notification could exist but invocation would fail.

## 18. Current Design Constraints

This implementation is good for local learning and prototyping, but there are some important constraints.

### 18.1 File type detection is extension-based

The routing decision uses the filename suffix, not deep MIME validation.

### 18.2 CSV decoding assumes UTF-8

Non-UTF-8 CSV files will fail unless decoding logic is expanded.

### 18.3 The DynamoDB key is the object key

Uploading the same object key again overwrites the existing metadata item.

### 18.4 `uploaded_at` is generated by Lambda

It is not the actual S3 event time or S3 object creation timestamp.

### 18.5 The function processes inline

There is no queue, retry orchestration layer, or dead-letter queue between S3 and Lambda.
